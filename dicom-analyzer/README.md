# Контроль качества DXA-снимков: сервис (прототип)

Один DICOM-файл на вход, словарь с результатами на выход. Сервис работает через NATS JetStream (`service.py`), как библиотека (`QCService`) или из консоли (`main.py`). Для отрисовки результата на снимке есть отдельный `render.py`.

## Docker и NATS

Из корня репозитория, после заполнения `.env` по `.env.example` и запуска NATS/Orthanc:

```bash
make run-analyzer-build
docker compose -f dicom-analyzer/compose.yaml logs -f
make stop-analyzer
```

Compose использует общую внешнюю сеть `dicom-network`. Веса и файлы порогов
монтируются из `dicom-analyzer/models/` только для чтения. Образ рассчитан на CPU,
запускается непривилегированным пользователем; веса не включаются в образ.
Без весов сохраняется описанный ниже запасной режим анализа.

Для локального запуска: установить `requirements.txt`, экспортировать переменные
окружения и выполнить `python service.py` (`.env` автоматически читает только Compose).

| Переменная | Значение по умолчанию / назначение |
|---|---|
| `NATS_URL` | `nats://localhost:4222`, несколько адресов через запятую |
| `NATS_REPLICAS` | `1`, в Compose — `3`; для создания потока |
| `DICOM_ANALYZER_PASSWORD` | Пароль пользователя `dicom-analyzer`; пустой — без аутентификации |
| `ORTHANC_HOST`, `ORTHANC_PORT` | `localhost`, `8042`; в Compose хост `orthanc` |
| `ORTHANC_NAME`, `ORTHANC_PASSWORD` | Пользователь и пароль Orthanc |
| `ORTHANC_TOKEN` | Если задан, заменяет base64 пары логин:пароль в Basic Authorization, как у manager |
| `MODELS_DIR` | По умолчанию `models/` рядом с кодом |
| `APP_NAME` | `dicom-analyzer`, имя сервиса в логах и трассах |
| `LOG_LEVEL` | `INFO` |
| `METRICS_ADDR` | `:9100`, HTTP endpoint `/metrics` |
| `TRACING_HOST`, `TRACING_PORT` | `localhost`, `4318`; в Compose — `otlp-collector:4318` |
| `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` | Необязательный полный URL OTLP HTTP, включая `/v1/traces`; заменяет `TRACING_HOST`/`TRACING_PORT` |

**Важно:** `ORTHANC_TOKEN` должен содержать действительный Basic-токен. Для
аутентификации через `ORTHANC_NAME`/`ORTHANC_PASSWORD` оставьте его пустым;
значение-заглушка `orthanc-token` не является рабочим токеном.

Analyzer читает `dicom.analysis.requested` из `DICOM_EVENTS` durable-подписчиком
`analyzer-requests`. Контракт v1 совпадает с `dicom-worker/pkg/events`:

```json
{
  "version": 1,
  "event_id": "cecfbb04-596a-43fd-9174-e4a6f7683600",
  "job_id": "22d969f6-3936-4e4b-ac76-35d441296f48",
  "dicom_id": "orthanc-instance-id",
  "status": "pending",
  "occurred_at": "2026-09-28T10:00:00Z"
}
```

`dicom_id` — идентификатор instance в Orthanc. Файл скачивается по
`/instances/{dicom_id}/file`, обрабатывается `QCService` и удаляется.
Настройки критериев используются по умолчанию: контракт v1 не содержит `settings`.
Ответ сохраняет `job_id` и `dicom_id`, получает собственные `event_id`/`occurred_at`:

- `dicom.analysis.completed`: `status: completed`, `result` с полями
  `anatomical_region`, `confidence`, `violations`, `duration_ms`, `metadata`.
- `dicom.analysis.failed`: `status: failed`, непустое `error`, без `result`.

ACK отправляется только после подтверждения публикации JetStream. При сбое связи
или временной ошибке Orthanc запрос повторяется через 5 секунд. Некорректный
конверт завершается TERM; ошибка анализа или отсутствие DICOM публикует `failed`.
Во время обработки каждые 20 секунд продлевается ACK deadline. Стабильный
`Nats-Msg-Id` результата обеспечивает дедупликацию в пределах окна потока (10 минут
при создании analyzer); повторный анализ после сбоя возможен. Один процесс
обрабатывает один снимок одновременно. SIGTERM/SIGINT прекращает получение новых
заданий после завершения текущего; Compose ждёт до 5 минут.

Тесты транспорта без ML-зависимостей:

```bash
cd dicom-analyzer
pip install prometheus-client opentelemetry-sdk opentelemetry-exporter-otlp-proto-http nats-py
python -m unittest discover -s tests -v
```

Интеграционный тест с настоящим JetStream и правами ролей из `docker/nats.conf`
(ML и HTTP заменены тестовыми ответами; нужен `nats-py`):

```bash
docker compose -p analyzer-test -f ../docker/test-compose.yaml up -d nats-auth nats-auth-2 nats-auth-3
TEST_NATS_URL=nats://localhost:14223 python -m unittest discover -s tests -v
docker compose -p analyzer-test -f ../docker/test-compose.yaml down -v
```

Используйте отдельный тестовый NATS: тест создаёт рабочие stream/consumer с их
стандартными именами и публикует тестовые задания.

## Быстрый старт

```bash
pip install -r requirements.txt                 # numpy, opencv, scipy, pandas, pydicom, torch, timm, albumentations
python main.py снимок.dcm                       # напечатает JSON результата
python main.py снимок.dcm --overlay out.png     # + картинка с разметкой (отладка)
python render.py снимок.dcm --result result.json -o out.png    # эталонная отрисовка по готовому результату
```
```python
from main import QCService
svc = QCService()          # один раз при старте сервиса
svc.warmup()               # загрузить все модели сразу (иначе грузятся при первом снимке); ~13 с, ~1 ГБ памяти
result = svc.process("file.dcm")                                  # словарь результата
result = svc.process("file.dcm", {"trochanter_center_mm": 3.0})   # с параметрами (см. ниже)
```
Весов моделей в репозитории нет — они слишком много весят и передаются отдельно. Их нужно положить в `models/` рядом с файлами порогов `*_gate.json` (список файлов ниже). Без весов сервис работает: регион определяется по маске кости и ширине снимка, а критерии, которым нужна модель, возвращают `ok: null` (не оценён). Один снимок обрабатывается около 0.3–1 с на процессоре (CPU).

## 1. Что возвращает `process`

Формат верхнего уровня совпадает с `model.JobInfo` из `swagger.yaml` коллеги:

| поле | тип | что значит |
|---|---|---|
| `status` | `"completed"` / `"failed"` | обработка завершена или упала (нет файла, не определена сторона бедра, неверные параметры) |
| `anatomical_region` | `"spine"` / `"hip_left"` / `"hip_right"` | что за снимок; `hip_left` / `hip_right` — сторона так, как размечено в проекте (`hip_left` = левое бедро на снимке) |
| `confidence` | число 0..1 | уверенность классификатора региона: `0.5·(доля согласных голосов) + 0.5·(уверенность сети)`; без весов сети — просто доля согласных голосов |
| `violations` | список строк | найденные нарушения на русском («Ось позвоночника отклонена более чем на 5°», «Область интереса: верх < 3 см» и т. д.). Пустой список — снимок годен |
| `duration_ms` | целое | время обработки |
| `metadata` | словарь | всё остальное (ниже) |
| `error` | строка | только при `status: "failed"`; в этом случае `anatomical_region` и `confidence` равны `null`, `metadata` пустой |

### `metadata`

| поле | что значит |
|---|---|
| `shape` | `[высота, ширина]` снимка в пикселях. Все координаты ниже — в пикселях **исходного снимка** |
| `classification` | как определили регион: `source` (`vote`), `votes` (голоса сети / маски кости / ширины снимка: `spine` или `hip`), `agreement` (доля согласных, 0..1), `unanimous`, `n_peaks` (число пиков ширины кости, ≥ 6 — позвоночник), `cnn_confidence` (уверенность сети) |
| `criteria` | словарь критериев (ключи ниже). У снимка позвоночника три, у бедра три |
| `verdict` | `1` — все оценённые критерии в норме, `0` — есть нарушение, `null` — ни один критерий не оценён |
| `models` | какие модели подключены (`подключена` / `нет весов`) |
| `settings` | с какими параметрами считали (значения по умолчанию + присланные) |

### Единый формат критерия (`metadata.criteria.<ключ>`)

| поле | тип | что значит |
|---|---|---|
| `name` | строка | ключ критерия |
| `ok` | `1` / `0` / `null` | `1` норма, `0` нарушение, `null` не оценён (нет модели, нет данных) |
| `source` | строка | чем считали: `math` (математика), `model`, `vote`, `gate` (отсев по трём точкам), `none` |
| `value` | число или `null` | главное число критерия (градусы / миллиметры), если есть |
| `unit` | строка | единица `value`: `deg` или `mm` (пусто, если `value` нет) |
| `points` | словарь `имя → [x, y]` | точки для отрисовки |
| `regions` | список полигонов | области для закраски: каждый полигон — список `[x, y]`, замкнутый неявно (первую точку в конце повторять не нужно) |
| `details` | словарь | дополнительные поля критерия (у каждого свои, ниже) |
| `note` | строка | причина, если критерий не оценён или отказал (например, «три ключевые точки не найдены») |

**Система координат:** начало в левом верхнем углу снимка, `x` вправо, `y` вниз, единица — пиксель исходного снимка (без масштабирования и без зеркалирования). Масштаб снимка: 0.6 мм по X, 1.05 мм по Y (один сканер); значения в см и мм уже пересчитаны.

**Цвета.** В ответе цветов нет, их выбирает фронт. В `render.py` принято так: `ok: 1` — зелёный `(70, 200, 70)`, `ok: 0` — красный `(235, 60, 60)`, `ok: null` — серый `(170, 170, 170)` (критерий не оценён, обычно ничего не рисуем); жёлтый `(240, 210, 0)` только там, где уровень «проверить»: `lesser_trochanter.details.status` и `foreign_objects.details.verdict` (это не нарушение у вертела, а у предметов нарушение, `ok: 0`).

## 2. Что отдаёт каждый критерий и как это рисовать

### Позвоночник (`anatomical_region: "spine"`)

#### `spine_axis` — ось позвоночника
- `ok`: 1, если модуль угла ≤ 5°. `null`, если столб кости не найден (тогда `note` с причиной).
- `value`: угол оси в градусах, `unit: "deg"`. Знак: отрицательный — нижний конец оси левее верхнего (ось «ползёт» влево вниз), положительный — правее.
- `points`: четыре точки — `top_left`, `top_right` (левый и правый край столба кости в верхней строке), `bottom_left`, `bottom_right` (то же в нижней строке).
- **Рисовать:** ось — линия от середины отрезка `top_left`–`top_right` до середины отрезка `bottom_left`–`bottom_right`, цветом критерия (зелёный при `ok: 1`, красный при `0`), толщина 2 px. Четыре точки — заполненные кружки радиусом ~5 px. Рядом с осью подписать угол (`value`). Больше ничего не нужно: вертикаль и допуск 5° фронт может показать сам.
- `details`: пустой.

#### `pelvis_crest` — подвздошные кости (гребни) в кадре
- `ok`: 1, если гребень есть с обеих сторон. Решение по каждой стороне принимается голосованием методов (модель точек, классификатор «гребень в окне», математика; большинство голосов).
- `points`: `crest_left`, `crest_right` — точки гребней. **Есть только у той стороны, где гребень найден.** Если гребня нет, ключа нет.
- `details.confidence`: `{left, right}` — вероятность присутствия по модели точек (0..1); пустой, если модели нет.
- `details.square`: `{width_px, height_px, left_ok, right_ok}` — размер боковых окон (одинаковый для обеих сторон) и есть ли гребень слева / справа.
- **Рисовать:** два прямоугольника (окна), прижатые к нижним углам снимка:
  - левое: `x` от 0 до `width_px − 1`, `y` от `shape[0] − height_px` до `shape[0] − 1`;
  - правое: `x` от `shape[1] − width_px` до `shape[1] − 1`, те же `y`.
  - Цвет окна: зелёный, если `left_ok` / `right_ok` = `true`, красный, если `false` (это и есть «зелёный/красный квадрат» из задачи). Толщина рамки 2 px.
  - Точки `crest_left` / `crest_right` (если есть) — кружок радиусом ~6 px, зелёный, подпись «C-left» / «C-right».

#### `foreign_objects` — посторонние предметы (дужки лифчика, застёжки)
- `ok`: 1 — чисто; 0 — найден предмет.
- `ok: 0` в двух случаях: найдена **дужка** (`details.verdict = "ПРЕДМЕТ"`, надёжный признак) или только **застёжка/предмет без дужки** (`"проверить"`, подсказка слабее). Различает их `details.verdict`.
- `regions`: контуры найденных предметов (дужек и застёжки вместе, различить их по контуру нельзя; что именно найдено, говорит `details.verdict`).
- `details.verdict`: `"ПРЕДМЕТ"`, `"проверить"` или `"чисто"`.
- **Рисовать:** каждый полигон из `regions` залить полупрозрачным цветом (~35%) и обвести контуром 1 px; цвет: красный при `ПРЕДМЕТ`, жёлтый при `проверить`.
- Если модель не подключена: `ok: null`, `regions: []`, в `note` причина.

### Бедро (`anatomical_region: "hip_left"` или `"hip_right"`)

#### `hip_margins` — область интереса (отступы до краёв кадра)
- `ok`: 1, если все три отступа в норме: сверху ≥ 3 см, снизу ≥ 3 см, сбоку ≥ 2 см. Считается по маске кости (не по точкам модели).
- `points`: `apex` (верхушка большого вертела на кости), `lateral` (самая боковая точка кости), `ischium` (нижняя точка седалищной кости; может отсутствовать, если не найдена, тогда `bottom_cm: null` и `ok: 0`).
- `details`: `top_cm`, `bottom_cm` (число или `null`), `side_cm` — отступы в сантиметрах; `implant` — на снимке найден эндопротез (маска строится иначе).
- **Рисовать** (перпендикуляры от точки до края кадра):
  - от `apex` вертикально вверх до `y = 0`, подпись `top_cm`;
  - от `lateral` горизонтально до бокового края **по стороне бедра** (`anatomical_region`): у `hip_left` — до правого края (`x = shape[1] − 1`), у `hip_right` — до левого (`x = 0`). Не по тому, какой край ближе в пикселях: на сильно смещённом снимке точка может оказаться ближе к чужому краю. Подпись — `side_cm`;
  - от `ischium` вертикально вниз до `y = shape[0] − 1`, подпись `bottom_cm`.
  - Линии тонкие (1 px), цвета критерия; на конце у точки кружок радиусом ~4 px; значения подписывать «7.7 см» рядом с серединой линии.
  - Если `implant: true`, можно подписать «имплант».

#### `hip_keypoints` — три ключевые точки бедра (модель)
- `ok`: 1, если модель нашла **все три** точки (оценка присутствия ≥ порога из `models/hip_keypoints_gate.json` и точка лежит внутри маски кости). Иначе `ok: 0`, **`points` пустой** (ни одной точки не отдаём), ротацию не меряем.
- `points`: `greater_trochanter_apex` (большой вертел), `femoral_neck` (шейка бедра), `ischium` (седалищная кость).
- `details.confidence`: оценка присутствия каждой точки (0..1), считается всегда, даже если точка отвергнута.
- **Рисовать:** кружок радиусом ~7 px (контур 2 px), рядом буква: `V` — вертел, `N` — шейка, `I` — седалищная. Цвет: зелёный при `ok: 1`. Это **другие точки, чем в `hip_margins`**: точка вертела модели не совпадает с `apex` из отступов, не смешивать.

#### `lesser_trochanter` — малый вертел (ротация бедра)
- `ok`: 1 — расстояние до бугра в норме (или «проверить»); 0 — вне нормы; `null` — не измерили. Снимок, у которого не нашлись три ключевые точки, получает `ok: 0`, `source: "gate"`, пояснение в `note`.
- `value`: расстояние от края кости до бугра в **миллиметрах**, `unit: "mm"`. `0.0` — бугор не найден.
- `details.status`: **уровень**: `"норма"` — в окне нормы (по умолчанию 1.0–4.4 мм); `"проверить"` — за окном не более чем на 30% от центра (0.2–1.0 и 4.4–5.2 мм); `"плохой"` — дальше; `"не измерен"` — не измеряли (см. `note`). `"норма"` и `"проверить"` дают `ok: 1`, `"плохой"` — `ok: 0`. Окно меняется параметрами (ниже).
- `points`: `near` и `far` — левая и правая граница закрашенной области на строке пика (без отступа на прорисовку): `value` — это ровно длина отрезка между ними, не отдельно посчитанное число. Есть **у любого бедра, включая протез** (обе точки настоящие: определяются по силуэту кости, металл в расчёте не участвует, см. ниже).
- `regions`: полигон области бугра (обычно один); пуст, если бугор не найден.
- `details.implant`: найден эндопротез. Для протеза расстояние и область считаются отдельным методом (`qc/implant_trochanter.py`) по силуэту кости (маска фон/кость), без яркости и металла: трасируется реальный край кости, грубо находится излом (бугор), эти строки исключаются, и чистый край снизу и сверху соединяется прямой — «как будто бугра нет»; превышение над этой прямой и есть расстояние. Проверено на всех 3 протезах в данных: площадь совпала с экспертной разметкой.
- **Рисовать:** полигон залить полупрозрачным цветом (~35%) и обвести 1 px; цвет по `details.status`: норма — зелёный, проверить — жёлтый, плохой — красный; рядом подписать `value` в мм («8.5 мм»). Отрезок (перпендикуляр) — линия между `points.edge` и `points.ridge`, тот же цвет, с кружком на каждом конце: это и есть измеряемое расстояние.

## 3. Параметры, которые может присылать бэкенд

Второй аргумент `process(file, settings)` — словарь. Любой ключ можно не присылать (тогда значение по умолчанию). Неизвестный ключ или неверное значение → `status: "failed"` с текстом ошибки. Значения, с которыми считали, возвращаются в `metadata.settings`.

| параметр | по умолчанию | что значит |
|---|---|---|
| `trochanter_center_mm` | 2.7 | середина окна нормы расстояния до малого вертела, мм |
| `trochanter_tol_percent` | 63 | допуск нормы в процентах от центра, в обе стороны (норма = центр ± 63% → 1.0–4.4 мм); допустимо (0, 100] |
| `trochanter_yellow_percent` | 30 | ширина жёлтой полосы «проверить» за окном нормы, % от центра |

Остальные пороги (отступы 3 / 3 / 2 см, допуск оси 5°, пороги моделей) пока заданы в коде и в `models/*.json`.

## 4. Как устроен сервис

```
main.py                 QCService: warmup() и process(); нарушения (violations) собираются здесь
render.py               отрисовка результата на снимке (для фронта; моделей не запускает)
qc/
  pipeline.py           чтение DICOM, классификатор региона (голосование), вызов ветки
  region_vote.py        голосование трёх критериев региона: сеть + маска кости + ширина снимка (300±5 — позвоночник, 280±5 — бедро)
  spine_branch.py       ось, гребни, предметы
  hip_branch.py         отступы, три точки, малый вертел
  implant_trochanter.py малый вертел у протеза (см. details.implant выше) — отдельный метод, vendor не трогает
  settings.py           параметры и их проверка
  hub.py                реестр моделей (models/), пороги из json рядом с весами
  adapters.py, kp_model.py, crest_models.py, foreign_model.py   загрузка весов и инференс моделей
  crest_math.py         математический голос для гребней
vendor/                 математика: маска кости, отступы, ось, малый вертел, имплант
models/                 пороги моделей (*_gate.json, в репозитории); сюда же кладутся веса (в репозитории их нет, см. выше)
examples/               примеры результата и отрисовки
notebooks: train_region_classifier.ipynb, train_hip_keypoints.ipynb (обучение этих моделей на Kaggle)
```

### Модели (`models/`)

| файл | модель | что даёт | без неё |
|---|---|---|---|
| `region_classifier.pt` | ResNet-18, 3 класса | голос сети в классификаторе региона | регион по маске кости и ширине снимка |
| `hip_keypoints.pt` + `hip_keypoints_gate.json` | ConvNeXt-Tiny, 3 точки бедра | критерий `hip_keypoints`, опора вертела по шейке | `hip_keypoints: null`, вертел меряется без отсева |
| `pelvis_crest.pt` + `pelvis_crest_gate.json` | ConvNeXt-Tiny, точки гребней | голос модели и точки `crest_left/right` | голосует одна математика, точек нет |
| `pelvis_presence.pt` | классификатор «гребень в окне» | голос в решении «гребень есть» | как выше |
| `foreign_seg.pt` + `foreign_seg_gate.json` | ResNet-18, сегментация | критерий `foreign_objects` | `foreign_objects: null` |

Пороги решений лежат в `*_gate.json` рядом с весами: порог присутствия точек бедра, три порога голосов гребней, параметры очистки масок предметов.

## 5. Когда снимок падает (`status: "failed"`)
- файл не читается;
- для бедра не определена сторона (нет ответа сети и нет кости в верхней части кадра);
- неверные параметры в `settings`.
Порог уверенности классификатора региона снимок **не отклоняет**: класс отдаётся всегда, низкая уверенность видна по числу `confidence`.

## 6. Что проверено и что нет
- Загрузка и совпадение весов с кодом моделей проверены по каждому файлу; на реальных DICOM полностью прогнано несколько снимков (бедро и позвоночник).
- Прогона на всём наборе снимков нет; честной метрики для критерия предметов нет (модель обучена на 19 позитивах, оценена только на обучающих снимках); точка гребня отличается от разметки в среднем на ~21 px.
- Отступ сбоку считается до края кадра. В данных у бедра есть чёрная полоса из нулей со стороны бокового края (у 148 из 153 снимков, до 6.5 см); рамки со всех сторон, как на картинке из ТЗ, в данных нет. Организаторам стоит уточнить, до чего считать этот отступ.
