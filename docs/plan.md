# План работы: DXA quality-control сервис

## Шаг 0 — Инфраструктура данных (до любого ML)

1. **DICOM-loader**: `pydicom` для чтения, извлечения `PixelData`, тегов, `study_uid`/`image_uid`. Нормализация пикселей (VOI LUT / windowing через `pydicom.pixel_data_handlers.apply_voi_lut`).
2. **Дедупликация**: хэш пикселей (`hashlib.md5(pixel_array.tobytes())`) → группировка файлов (в нашем train-наборе 499 файлов → 252 уникальных изображения) в уникальные изображения. Таблица `image_hash → [file_paths]`.
3. **Датасет-реестр**: единый CSV/Parquet: `study_uid, patient_id, image_hash, file_path, region_label, quality_labels..., fold` — на него потом ссылаются все обучающие скрипты, а не на разметка.xlsx напрямую.
4. **Разбиение train/test (и train/val по фолдам) — строго по пациенту, а не по файлу и не по изображению.**
   - Все файлы одного `study_uid` (а если есть межисследовательская связь по пациенту — то и все study одного пациента) должны целиком попадать в один и тот же сплит.
   - Это критично из-за дублей: у нас 44 исследования из 100 имеют по несколько копий одного и того же снимка (одинаковые пиксели, разные `SOPInstanceUID`/дозовые теги). Если разбивать по файлам случайно, копии одного снимка могут оказаться и в train, и в val/test одновременно — модель будет "подсматривать" ответ, метрики завысятся и не будут отражать реальное качество на новых пациентах (data leakage).
   - Технически: `StratifiedGroupKFold` из `scikit-learn`, где `groups = study_uid` (или `patient_id`, если он доступен и стабилен), `y = quality_class` для стратификации по балансу классов.
   - 5-fold по этому принципу для кросс-валидации; финальный внутренний hold-out (если нужен отдельно от closed test) — тоже с группировкой по пациенту.

Инструменты: `pydicom`, `pandas`, `scikit-learn` (`StratifiedGroupKFold`).

## Шаг 1 — Классификатор анатомической области (region classifier)

**Задача**: снимок → {позвоночник, правое бедро, левое бедро}.

**Модель**: лёгкий CNN-backbone с ImageNet/RadImageNet весами — **ResNet18/34** или **EfficientNet-B0** из `timm`. При ~250 уникальных картинках это самая надёжная и быстрая победа (высокая точность ожидаема, классы визуально сильно различаются).

**Веса для переноса**: RadImageNet (обучен на медицинских снимках, а не на ImageNet-котиках — обычно даёт прирост на рентгене):
- [BMEII-AI/RadImageNet](https://github.com/BMEII-AI/RadImageNet) — официальный репо, веса ResNet50/DenseNet121/InceptionV3
- [GKalliatakis/radimagenet-pytorch](https://github.com/GKalliatakis/radimagenet-pytorch) — PyTorch-порт

**Обучение**: fine-tune последних 1–2 блоков + голову, заморозив ранние слои (иначе переобучится на малом датасете). Аугментации: горизонтальный флип **с одновременной переменой метки** лево/право-бедро, лёгкий crop/scale/яркость, без сильных геометрических искажений (не портим анатомию).

**Валидация**: 5-fold по `study_uid`/пациенту, accuracy/F1 по 3 классам.

**Fallback**: правило по ширине снимка (эвристика 300px/280px) как sanity-check/second opinion, но не единственный источник истины (не переносится на другой аппарат/разрешение).

## Шаг 2 — Детекция анатомических ориентиров (landmark/keypoint model)

Это ядро решения — вокруг него строится вся геометрия критериев.

**Позвоночник**, точки:
- верхние края подвздошных костей (2 точки)
- середина тела Th12 (1 точка)
- набор точек вдоль оси позвоночника (5–7 точек по центрам тел позвонков) — для фитинга линии оси и угла наклона

**Бедро**, точки:
- вершина большого вертела
- верхняя точка шейки бедра
- седалищная кость
- контур в зоне малого вертела (3–5 точек контура — по ним считается "плавность"/деформация для оценки ротации)
- крайние точки поля скана (для расчёта отступов ROI)

**Архитектура**: heatmap-based keypoint regression — на каждую точку своя тепловая карта (гауссиана вокруг истинной координаты), сеть предсказывает heatmap, координата = argmax.

**Модели-кандидаты**:
- **HRNet** (High-Resolution Net) — золотой стандарт для точной локализации точек, сохраняет высокое разрешение через всю сеть:
  - [HRNet/deep-high-resolution-net.pytorch](https://github.com/HRNet/deep-high-resolution-net.pytorch) (оригинал, CVPR2019)
  - [HRNet-for-Fashion-Landmark-Estimation.PyTorch](https://github.com/svip-lab/HRNet-for-Fashion-Landmark-Estimation.PyTorch) — хороший референс именно для landmark-heatmap регрессии (не поз человека, а точечных ориентиров) — по структуре ближе к нашей задаче, чем pose-estimation репо
- Более лёгкая альтернатива при ограниченных ресурсах: **U-Net-подобная сеть с heatmap-головой** на backbone ResNet34 — проще обучать на малом датасете, меньше риск переобучения, чем полный HRNet.

**Похожие работы по предметной области** (для обоснования подхода на питче):
- [VerteNet — гибридная CNN-Transformer модель для точек позвонков именно на lateral spine DXA](https://arxiv.org/html/2502.02097v1) — максимально близкая к нашей задаче работа
- [Deep Learning-based Detection of Hip Anatomical Landmarks in X-ray Images](https://pmc.ncbi.nlm.nih.gov/articles/PMC13544418/) — двухстадийная VGG16/ResNet50 модель (сначала bbox landmark-а, потом точная точка внутри) — хороший вариант, если heatmap-подход даст нестабильные результаты на малых данных
- [Automatic landmark detection, whole-spine lateral radiographs](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC8027006/) — методология аннотирования и обучения на похожем объёме данных

**Как размечать точки** (готовой keypoint-разметки нет):
1. Разметить вручную keypoints на ~100–150 "хороших" (корректных) снимках через простой инструмент — [CVAT](https://www.cvat.ai/) поддерживает keypoint-разметку из коробки, либо Label Studio.
2. Для нарушенных снимков (мало примеров) — **синтетическая генерация**: берём корректный снимок с размеченными точками → поворачиваем на случайный угол (аффинное преобразование) → точки поворачиваются вместе с картинкой по той же матрице → получаем снимок+точки+ground truth угол без ручной разметки. Это резко увеличивает обучающую выборку для регрессии угла.
3. Активное дообучение: обученная на синтетике+ручной разметке модель прогоняется на оставшихся снимках, неуверенные/ошибочные предсказания поправляются вручную (человек правит только ошибки, не размечает с нуля) — так быстрее наращивать датасет.

**Обучение**: transfer learning с ImageNet/RadImageNet backbone, MSE/Adaptive Wing Loss на heatmap, аугментации — только affine-преобразования с пересчётом координат, без деформаций, которые ломают анатомию.

## Шаг 3 — Геометрический rule engine (постобработка над точками)

Не модель, а детерминированный код поверх координат из Шага 2:

- Угол оси = arctan между линией регрессии по точкам оси и вертикалью → сравнение с порогом 5°
- Уровень укладки = есть ли в кадре точки подвздошных костей и середина Th12 (по их координатам относительно границ снимка)
- Ротация бедра = степень отклонения контура малого вертела от эталонной формы (можно обучить лёгкий классификатор поверх вектора координат контура: SVM/логрегрессия на few-shot, т.к. это уже не картинка, а 5–10 чисел)
- ROI-отступы = расстояние от крайних точек анатомии до края поля скана, переведённое в см (нужен PixelSpacing/фиксированное значение — зависит от ответа оргов)

Это даёт объяснимость: на демо показываем не "чёрный ящик сказал брак", а конкретный угол/расстояние с визуализацией точек и линий.

## Шаг 4 — Детектор посторонних объектов/артефактов

**Задача**: бинарный флаг + (опционально) локализация металлических артефактов/инородных предметов.

**Вариант А (проще)**: бинарный классификатор аномалии — **anomaly detection / one-class подход**, т.к. позитивов очень мало. Автоэнкодер или PatchCore на "чистых" снимках → артефакт = область с высокой ошибкой реконструкции.

**Вариант Б (если позитивов наберётся десяток+ через доразметку)**: лёгкий детектор **YOLOv8-nano** ([ultralytics/ultralytics](https://github.com/ultralytics/ultralytics)) с **copy-paste аугментацией** — вырезаем артефакт с реального снимка, вставляем в правдоподобные места (по краям кадра, в проекции одежды) на чистые снимки, генерируя синтетические позитивы с точным bbox.

## Шаг 4.1 — Бонус-фича: автоматическая коррекция разметки с подтверждением специалистом (п.2.6 ТЗ)

**Суть фичи**: не накопление датасета (это лишь побочный эффект), а помощь врачу/рентгенолаборанту здесь и сейчас. Сервис не просто сообщает "укладка/разметка некорректна", а сам предлагает исправленный вариант — например, как должна проходить ось позвоночника, где должны быть границы ROI/поля сканирования — и показывает это предложение в UI поверх снимка. Специалист одним действием подтверждает предложение или поправляет его вручную, вместо того чтобы размечать с нуля.

**Реализация**: отдельной модели не требуется — используется та же keypoint-модель из Шага 2/3 (ось позвоночника, границы ROI, контур ротации бедра), применённая в инференсе к новому снимку. Нужны:
- UI-компонент для отображения предложенной разметки поверх изображения и её редактирования (например, перетаскивание точек)
- backend-эндпоинт, принимающий решение врача (подтверждено / изменено на такие-то координаты)
- хранилище для этих подтверждений/правок (привязка к `study_uid`/`image_uid`, версия, флаг `confirmed_by_expert`)

**Важно**: подтверждения специалиста стоит логировать как feedback-датасет для будущего ретрейна, но сам ретрейн должен оставаться управляемым офлайн-процессом (см. раздел про переобучение ниже), а не автоматическим — иначе нарушается требование воспроизводимости результатов (п.2.7 ТЗ) и это риск для клинического ПО без валидации новых весов человеком перед выкаткой.

## Шаг 5 — Агрегация и отчёт

Код (не модель), собирающий выходы шагов 1–4 в строки требуемой схемы (`path_to_study`, `study_uid`, `image_uid`, `anatomical_region`, `quality_class`, `violation_type`, `processing_status`, `time_of_processing`). Обёртка try/except на каждое изображение — при ошибке `processing_status=Failure`, но пайплайн не падает целиком.

---

## Шаг 6 — Валидация и метрики

- 5-fold CV по `study_uid`/пациенту (см. Шаг 0, п.4) — без утечки дублей между train и val
- Метрики по каждому шагу отдельно: accuracy region-classifier, MAE угла в градусах, Dice/PCK для keypoints, F1/ROC-AUC для итогового `quality_class`
- Бутстрэп по фолдам → 95% доверительные интервалы
- Отдельный анализ ошибок: где geometric engine расходится с "Итог" из разметки (кейсы со сколиозом/переломом, где формальные критерии и итоговая метка не совпадают)

## Порядок реализации (спринты)

| Спринт | Что делаем | Модель |
|---|---|---|
| 1 (MVP) | Loader + дедуп + group-split по пациенту + region-classifier + простой end-to-end бинарный `quality_class` для позвоночника | ResNet18 (RadImageNet init) |
| 2 | Keypoint-модель для позвоночника (ось + уровень укладки) + rule engine | HRNet-lite / U-Net+heatmap |
| 3 | Keypoint-модель для бедра (ротация + ROI) + rule engine | та же архитектура, отдельные веса или общий backbone |
| 4 | Детектор артефактов + бонус-визуализация (маска/heatmap в отчёте) | YOLOv8-nano или autoencoder |
| 5 | Docker, API, документация, метрики с ДИ, презентация | — |

Так каждый спринт даёт рабочий прирост функционала, а не "всё или ничего" в конце.
