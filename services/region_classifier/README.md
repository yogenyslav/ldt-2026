# Region classifier (OpenCV, без обучаемых моделей)

Первая итерация классификатора анатомической области DXA-снимка
(позвоночник / бедро) и стороны бедра, чисто на классическом CV —
без нейросетей и обучения. Цель: быстрый MVP-baseline и sanity-check
перед переходом на ML-подход из [`docs/plan.md`](../../docs/plan.md).

## Метод

1. **Сегментация кости**: Otsu-порог + морфологическое открытие/закрытие
   + самая большая связная компонента (кость ярче и крупнее фона/шума).
2. **Классификация зоны — по периодичности силуэта**: считаем ширину
   кости построчно (сумма ярких пикселей маски в каждой строке) и ищем
   локальные максимумы этого профиля. На позвоночнике чередование
   "тело позвонка — межпозвонковая щель" даёт много пиков (обычно 5+),
   на бедре силуэт монотонно расширяется к головке/тазу без выраженной
   периодичности (обычно 2-4 пика).
3. **Ширина снимка как вторичный сигнал**: на исследованных данных
   (единственный аппарат, GE Lunar Prodigy Advance) ширина снимка
   почти всегда 300px для позвоночника / 280px для бедра. Используется
   как подтверждающий, а не основной признак — он завязан на конкретный
   аппарат/экспорт и не обязан переноситься на закрытый тест.
4. **Сторона бедра — концентрация массы кости в верхней трети кадра**:
   в верхней части снимка бедра находится крыло подвздошной кости,
   которое даёт выраженный сдвиг центра масс влево/вправо от центра
   кадра. Мы считали этот же признак по всему кадру и по верхней трети —
   по всему кадру сигнал слабее (диафиз кости внизу почти по центру
   "размывает" асимметрию), по верхней трети — устойчивее. Подробности
   и цифры сравнения — в переписке команды.

   **Важно**: "image_left"/"image_right" — сторона в координатах
   изображения, не гарантированно совпадает с анатомическим
   "левое/правое бедро" пациента (зависит от конвенции укладки). Нужно
   свериться на нескольких снимках с известной стороной.

## Точность (честная оценка)

Прямой поимённой (per-image) разметки зоны у нас нет — организаторы
предоставили только study-level разметку критериев качества
(`разметка.xlsx`). Поэтому оценка идёт через сверку с собственной
эвристикой команды по ширине снимка (300/280 px) — тоже не истинная
метка, а вторая независимая эвристика.

Результат на всех 497 читаемых файлах обучающего набора
(`НД_для_обучения/Исследования`):

```
python eval_against_width_heuristic.py "<путь>\НД_для_обучения\Исследования"
```

- **Точность признака формы (периодичность), без подмешивания ширины: 99.6%**
  (495 / 497 совпадений с width-эвристикой).
- Достигнуто подбором (grid search по числовым константам, не обучением
  модели) параметров сегментации и поиска пиков:
  - добавлен **CLAHE** (локальное выравнивание контраста, `clipLimit=3.0`)
    перед Otsu-порогом — это и был основной прирост точности (с ~88.5%
    до 99.6%). Причина: часть снимков позвоночника были низкоконтрастными,
    Otsu без предварительного выравнивания сегментировал их не полностью,
    периодичность (чередование позвонков) терялась, и такие снимки
    ошибочно уходили в класс "бедро".
  - морфологическое ядро уменьшено с 5×5 до 3×3 (меньше "съедает"
    мелкие детали контура);
  - порог по числу пиков повышен с 5 до **6** (часть корректно
    сегментированных позвоночников давала именно 5-6 пиков, не 5+, порог
    подбирался по сетке значений, а не угадан).
  - точные значения — см. константы в начале `classify.py`
    (`CLAHE_CLIP_LIMIT`, `PEAK_SMOOTH_WINDOW`, `PEAK_PROMINENCE`,
    `PEAK_MIN_DISTANCE`, `SPINE_PEAK_THRESHOLD`).
- Итоговый blended-результат (с fallback на ширину при разногласии
  сигналов) с новыми параметрами совпадает с shape-only результатом
  (ширина больше не меняет решение — признак периодичности стал точнее
  самой ширины и теперь является основным, а не вторичным сигналом).

## Ограничения

- Оставшиеся 2 ошибки из 497 (0.4%) — снимки бедра с выраженной
  трабекулярной (губчатой) текстурой кости низкой плотности: CLAHE
  усиливает эту текстуру, силуэт получается "рваным" и даёт ложные
  пики, похожие на периодичность позвонков. Возможно, коррелирует с
  реальным остеопорозом у пациента — стоит иметь в виду.
- Сторона бедра (`image_left`/`image_right`) не верифицирована против
  истинной анатомической стороны — нужна ручная проверка на выборке.
- Метод не умеет работать с несколькими типами аппаратов/экспортов —
  калибровался только на данных из `НД_для_обучения` (единственный
  аппарат, GE Lunar Prodigy Advance).
- Оценка (99.6%) — это сверка с эвристикой по ширине снимка, а не с
  истинной per-image разметкой (её нет). Если ширина сама в чём-то
  ошибается, эта ошибка не будет обнаружена такой оценкой.
- Задуман как **fallback на случай отказа основной ML-модели**
  (region-classifier из `docs/plan.md`, Шаг 1), а не как замена ей —
  ML-версия сможет учитывать больше контекста и переноситься на другие
  аппараты/экспорты, чего эта чисто геометрическая эвристика не умеет.

## Использование

```bash
# один файл
python classify.py path/to/study.dcm

# рекурсивно по папке с исследованиями
python classify.py "C:\path\to\НД_для_обучения\Исследования"
```

Вывод построчно: `region`, `conf` (эвристическая уверенность),
`n_peaks`, `width_hint`, и для бедра — `side` со знаком уверенности.
